# Magpie 插件 1.0.3：修复旧 MCP 占用导致的升级启动失败

适用于 FISH Dock 1.1.0+、Windows x64、宿主 API 1。仅 Magpie 适配插件升级为 **1.0.3**；飞书、Clash 和 OFM 保持已发布的 **1.0.2**。随包 Magpie 原生程序仍为官方 **0.1.1709**，原始字节和许可证保持不变。

## 已确认的问题

1.0.2 启动时将随包程序复制到插件资料内固定的 `credentials/magpie-runtime/magpie.exe`，随后替换旧文件。用户的 DSH NEXT、Codex 已把这个路径作为 `mcp image` 服务使用，旧进程即使不监听 Dock 管理页端口，也一直占用程序。Windows 在替换处返回 `EPERM`，启动中止，页面却显示通用路径/端口错误。客户端还会自动重连，因此仅结束一次 MCP 不能根治。

此前 64 项自动回归未覆盖“外部旧 MCP 仍运行时准备新版程序”，不足以证明这类升级可用。本版添加对应失败回归并更改实现。

## 改动

- 运行副本使用同目录 `magpie-<SHA-256>.exe`，不同原生版本并存；升级新增并选择完整副本，绝不覆盖旧 MCP 使用的固定程序。
- 每次准备核验实际副本内容，旧 `source.sha256` 标记不再决定副本可信性。损坏副本会阻止启动并提供明确错误，保留原文件和资料供检查。
- 副本先写入本次独有临时文件并校验，再在同目录用 NTFS 硬链接独占发布。并发者只能采用通过摘要校验的完整目标，本次临时文件结束时清理。
- 原便携资料仍为 `credentials/magpie-runtime/data/`。只在目标缺失时迁移旧 `credentials/magpie/`，现有账号、渠道、插件和资料保持原位置；旧程序、旧源标记及过去失败留下的文件不会自动删除。
- 准备资料、准备托管更新设置、校验运行文件、等待进程就绪分阶段反馈。资料迁移、访问权限、运行文件完整性与启动错误使用固定脱敏文案。
- 原生自更新关闭、内部插件页面嵌入修复、第三方中转静默流保活等 1.0.2 行为保留。停止 Dock 管理服务只回收自身服务，不结束外部 MCP。

## 验证

最终完整回归 **70 项全部通过，0 失败、0 跳过**，启用真实 Magpie、mihomo、OFM、宿主 SDK 和隔离 Edge。

新增的真实升级夹具从已发布 1.0.2 的资源启动 `mcp image`，完成 MCP initialize/ping 后保持连接：

1. Windows 对旧程序的替换明确返回 `EPERM`。
2. 新适配层在同一资料根准备不同文件名的程序，旧 MCP 继续响应 ping。
3. 新管理服务启动、Cookie 登录就绪检查通过。
4. 停止新管理服务后，旧 MCP 仍能 ping；合成业务资料保持。

另覆盖不同摘要版本并存与回选、旧自更新副本和源标记保留、损坏副本阻止运行、并发发布完整性和临时文件收尾、启动阶段和就绪后实际运行摘要。

资源回选仅针对程序文件，不代表任意跨原生版本的数据格式降级都可行。本版原生仍是 0.1.1709；未来原生 schema 变化需要另外验证迁移和恢复。真实 Dock WebView2 全部安装/卸载矩阵、所有第三方内部插件与真实模型业务仍保留跟踪，Issue #3 不自动关闭。

## 更新

在 Dock「插件」页刷新商店并更新 **Magpie 1.0.3**，随后启动服务。也可下载同版 `magpie.fish-plugin` 并核对 `SHA256SUMS.txt`。npm 包为 `@fish-under-sea/fish-dock-plugin-magpie@1.0.3`。其他插件继续使用 1.0.2。
