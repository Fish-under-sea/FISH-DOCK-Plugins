# 自启动按钮钩子（`behaviors.autostart`）

> 面向插件作者：这是**唯一**一个"插件告诉宿主怎么画按钮、宿主告诉插件这次是不是自启动"的钩子。写错的代价不是按钮难看，而是服务该起的时候没起、不该起的时候抢跑。

## 1. 两个方向的约定只有一条

| 方向 | 载体 | 含义 |
| --- | --- | --- |
| 插件 → 宿主 | 清单里的 `behaviors.autostart` | 这颗按钮要不要出现在 Dock 插件卡上，以及出现时的两种文案 |
| 宿主 → 插件 | 环境变量 `FISH_PLUGIN_AUTOSTART=1` | **仅"随 Dock 启动"这一次**为 `1`；其余所有启动路径都不传 |

## 2. 清单值与卡面

| `behaviors.autostart` | 卡面表现 | 会不会传 `=1` |
| --- | --- | --- |
| `true` | 「随 Dock 启动 / 已关闭」两态胶囊 | 打开的那一次启动传 `1` |
| `false` | 灰色小字「无需自启动」，不占按钮语义 | 永不传 |

- 有本机服务的插件（Clash、Magpie）写 `true`；
- 没有本机服务的插件（飞书）写 `false`，**并且不要去读这个环境变量**——读了也没有意义，只会让人误以为有自动行为；
- 清单由 `tools/stage-development.mjs` 按 `definitions` 的 `autostart` 字段生成，**不要手改打包后的 `plugin.json`**，否则下次打包就被覆盖。

## 3. 语义边界（最容易写错的地方）

`FISH_PLUGIN_AUTOSTART=1` 只代表一件事：**这一次是用户"随 Dock 启动"带起来的**。下列路径一律**不传**：

- 首次安装；
- 用户在插件卡上点「启用」；
- 版本回滚；
- 用户手动启动内核 / 手动打开页面；
- 插件崩溃后宿主重启它。

所以 `activate()` 里不要写成"只要没有服务在跑就拉起"——那是把用户的手动行为也当自启动。正确写法：

```javascript
activate:async context=>{
  service=createGateway({context,runtime:createRuntime(context),kind:'acme'});
  await service.load();
  // 只有「随 Dock 启动」这一次把本机服务拉起来；其余路径等服务被用户点到。
  if(process.env.FISH_PLUGIN_AUTOSTART==='1'&&service.view().state==='stopped')void service.start().catch(()=>{});
},
```

三个细节：

1. **`view()` 可能是异步的**（例如 Clash 要读控制器状态）：先 `await` 再读 `.state`，别把 Promise 当对象；
2. 启动失败要 `catch` 掉并让页面能重试，**不要让 `activate()` 抛出去**——`activate` 失败会让整个插件停用，用户看到的是"插件坏了"；
3. 已经在运行时保持原样，不要重复 spawn（会产生第二个内核/服务进程）；
4. **准备阶段失败也要进重试**：读配置、修内核/可执行路径、探控制器这些"起服务之前"的失败，与启动失败共用同一条退避（0 / 1.5 / 4 秒），不要打一行「自启动准备失败」就结束。冷启时磁盘与端口都慢一拍，第一轮失败是常态；只重试 `start()`、把准备段留在重试之外，等于把最常见的那次失败固定成"第一次开机起不来"；
5. **`view()` 每轮自启只读一次**：判断、日志、修复都用同一份快照。多次读盘既慢，又可能两读之间状态已经变了；异步实现（Clash 的控制器状态）必须先 `await` 再判断。

## 4. 只有一处开关

自启动开关**只在宿主插件卡上**有：

- 插件页面里**不要**再放一个自启动开关；
- 页面**不要**去调什么 `dock.autostart` 之类的方法；
- 两处都有，状态必然打架（用户关了卡片上的、页面里还是开的）。

## 5. 冷启动阶段为什么常"看起来失败"

宿主是异步起的，插件页与插件服务可能比它还早。作者常报"第一次开机按钮点了没反应、第二次就好了"，实际多是下面三类原因（2.1.3 的诊断结论）：

| 现象 | 真实原因 | 作者侧能做的 |
| --- | --- | --- |
| 首启页面报错或空白，稍后自愈 | 宿主安装/激活期持锁，页面 RPC 被堵过 20 s 判定超时 | 页面区分「宿主太旧」与「服务正在启动」，后者退避重试（1/2/4 s × 3），不要把超时当"需要更高版本" |
| 图标、供应商列表首启缺失 | 预装/素材还在装（上游更新循环在后台按 npm spec 装） | 素材与列表按"可缺失"设计，缺了显示占位而不是报错 |
| 自启动那一次服务没起来 | `activate()` 里把 `FISH_PLUGIN_AUTOSTART` 判断写错，或 `view()` 没 await | 按第 3 节写法，并在自测里逐条验 |

## 6. 自测清单（提交前四条都要过）

1. **写 `true` 的插件**：带 `FISH_PLUGIN_AUTOSTART=1` 启动 → 服务自动起来；不带 → 服务保持停止，直到用户点；
2. **写 `false` 的插件**：任何路径下都不读该变量，卡面显示「无需自启动」；
3. **重复启动**：服务已在运行时再走一次自启动路径 → 不产生第二个进程；
4. **`activate()` 里服务启动失败**（端口占用等）→ 插件仍然激活成功，页面能显示失败原因并重试；
5. **冷启慢盘**：人为让控制器/内核路径慢一拍（准备阶段失败一次），自启仍在 0 / 1.5 / 4 秒的退避内起来，日志只有最终一条结果，不是「准备失败」后静默。
